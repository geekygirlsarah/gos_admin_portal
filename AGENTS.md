# GoS Admin Portal — Agent Guidelines

These guidelines help coding agents (like Junie) understand the project, its structure, and how to contribute effectively.

## Critical Rules

- **Always follow Test-Driven Development (TDD):** When implementing a new feature or fixing a bug, YOU MUST first provide the test case that reproduces the issue or defines the new behavior. Only then provide the implementation.
- **Respect read-only mode:** Do not modify files unless explicitly asked.
- **Follow existing style:** Match the project's use of Black, Isort, and PEP 8.
- **No interactive commands:** All terminal commands must be non-interactive.
- **Don't make large assumptions:** If something is unclear, ask before making assumptions.

## Project Overview

Girls of Steel (GoS) Admin Portal is a Django 5 web application for managing:
- Programs and student enrollments
- Students (profiles, photos, school, graduation year, demographics)
- Adults (Parents, Mentors, Volunteers, Alumni) and their relationships to students
- Mentors/volunteers and their access/clearances
- Program fees, payments, fee assignments, and sliding-scale discounts
- Per-student balance sheets within a program
- Student attendance tracking via kiosks and RFIDs
- Public Applications wizard (`/apply/`) with a staff review workflow
- API access for external integrations (`/api/v1/`)

### Key Technologies
- Django 6.1
- django-allauth (Email OTP login)
- Bootstrap 5
- Pillow (Images)
- openpyxl (Excel)
- PostgreSQL in production, SQLite for local testing

## Repository Structure

- `AGENTS.md` — This file (project guidance for agents)
- `GoSAdminPortal/` — Settings, URLs, middleware (`LoginRequiredMiddleware`), allauth adapter
- `programs/` — Core app (programs, students, adults, fees, payments, sliding scale, enrollments)
- `applications/` — Public application wizard + staff review workflow (supersedes legacy `StudentApplication`)
- `attendance/` — Student check-in/out logic and RFID management
- `orders/` — Purchase/order requests (students/mentors place and edit their own pending items; Lead Mentors review, mark placed/shipped/received, archive received orders, delete, and export)
- `api/` — Kiosk API views and attendance endpoints
- `templates/` — Django templates organized by app/role
- `audit/` — Audit log app with `AuditLog` (immutable, append-only), `AuditEvent` choices, `log_event()` service, signal-based logging, `SensitiveDataViewMixin` (with program-scope tracking), and `audit/utils.py` unified query helpers. `AuditContextMiddleware` exposes the active request to signal handlers via thread-local storage (`audit/context.py`), so `pre_save` receivers on Student/Adult can attribute `PROFILE_LINK_CHANGED` events (account link set/cleared/switched) to the acting user.
- `portal/` — Inspect before use; may contain legacy or shared views

## Data Model Summary

- **Program**: Central entity with fees, features, and enrollments.
- **SchoolDistrict**: Canonical school districts (e.g. "North Allegheny School District"). `School.district` is a nullable FK to `SchoolDistrict` (`on_delete=SET_NULL`, related name `schools`), so a district can be deleted and schools simply become unassigned. Lead Mentors manage districts from the "Manage Districts" page (`school_district_list`/create/edit/delete) linked from the Schools page. Backfill from the legacy free-text `School.district` field happened in migration `0104`.
- **Student**: Identity (`legal_first_name`, `preferred_first_name`, `last_name`), school, graduation, demographics, medical, and relationships to adults. The portal `StudentForm` intentionally never exposes the linked `user` account field (a hidden/unsubmitted field would silently NULL out the link on save); only Django admin can edit it, via the `AdminStudentForm` variant. Both Student and Adult share the same name field naming convention: `legal_first_name` (required), `preferred_first_name` (optional), `last_name`. A `display_name` property returns `preferred_first_name or legal_first_name + last_name` — use this everywhere for display instead of manual fallback chains. The `full_name` property aliases `display_name` for backward compatibility. A student is considered **inactive** once marked `graduated=True`; within a program they're inactive if their `Enrollment.active` is `False` or they've graduated. When building student dropdowns/selection lists, reuse `active_students()` / `active_students_in_program(program)` in `programs/utils.py` so inactive students stay out. On program-scoped list pages, separate inactive students into their own section (as `programs/views.py` does for the program detail, assignment, photo grid, and dues-owed views). Student↔Adult links are stored in the `AdultStudentRelationship` through model (also the source of `Student.adults` / `Adult.students`). Each student's primary/secondary parent/guardian is normalized there via the `primary_contact_relationship` / `secondary_contact_relationship` FKs; `Student.primary_contact`, `Student.secondary_contact`, `Student.primary_contact_id`, and `Student.secondary_contact_id` are **compat properties** (with setters) that keep the through row and pointer in sync. When filtering on primary/secondary in queries, use the relationship FKs (e.g. `primary_contact_relationship__adult=...`) — never the compat property names. Allergy/dietary/medical info is stored in the encrypted `allergies`, `dietary_restrictions`, and `medical_notes` fields (the `"health_medical"` permission section). Mentors and Lead Mentors can view a per-program snapshot of these on the **Medical Info** page (`ProgramMedicalInfoView`, URL `programs:program_medical_info`, template `programs/medical_info.html`, linked from the program navbar menu and gated on `can_read user 'health_medical'`), which lists only active students who have at least one non-blank medical field. Lead Mentors can merge duplicate student records from the "Merge Students" page (`student_merge`, linked from the All Students list). The merge transfers all parent/adult relationships, updates primary/secondary contacts, fills in all missing profile/demographic/contact/medical fields from the source, preserves linked user accounts (via the shared `transfer_user_account()` helper in `programs/utils/accounts.py`), and moves/merges all associated records (enrollments, payments, fee assignments, signed student documents, background checks, sliding scale applications, RFID cards, attendance sessions/events, daily presence records, digital signouts, applications, outreach signups, and badges). Merges are logged via `AuditEvent.RECORDS_MERGED`.
- **Adult**: Unified model for Parent, Mentor, Alumni, Volunteer. Lead Mentors can merge duplicate parent records from the "Merge Parents" page (`parent_merge`, linked from the All Parents list). The merge transfers all student relationships, fills in all missing profile and contact fields from the source (including preferred first name, emergency contacts, notes, college/employer info, photo, and mentor/Andrew ID details; defaulted choice fields like `phone_type`/`state`/`role` are only treated as "missing" when the value they describe is missing too), merges role flags, transfers linked user accounts (via the shared `transfer_user_account()` helper in `programs/utils/accounts.py`), and moves/merges all associated records (background checks, mentor agreement acceptances/submissions, outreach mentor signups, RFID cards, sliding scale applications, and attendance sessions/events). Merges are logged via `AuditEvent.RECORDS_MERGED`.
- **Enrollment**: Links Student ↔ Program.
- **Fee**: Per-Program costs. Applicability (which students a fee applies to) is set inline on the add/edit fee form (`FeeForm` in `programs/forms.py`, which carries a `students` `ModelMultipleChoiceField` limited to `active_students_in_program`). An empty selection means the fee applies to every active student in the program; selecting students creates `FeeAssignment` rows restricting it to just those students. The legacy standalone applicability page/view (`FeeAssignmentEditForm`, `ProgramFeeAssignmentEditView`, URL `program_fee_assignments`) is still present but no longer linked from the fee list. Fee-added emails are governed by `notify_fee_parents()` in `programs/signals.py`: on creating a fee (via the view) parents are emailed **only** for the fee's applicable active students — the create view (`ProgramFeeCreateView.form_valid`) suppresses the `Fee`/`FeeAssignment` `post_save` notify signals during save and then calls `notify_fee_parents()` once, so a narrow selection never emails everyone first. Direct `Fee.objects.create()` still fires the `notify_parents_on_fee_added` signal, which routes through the same `notify_fee_parents()` helper.
- **Payment**: Recorded against a Fee for a Student.
- **SlidingScale**: Percent discount tied to a Student (not a single Program) with a `status` (`pending`/`approved`/`declined`), an effective `date`/`expiration_date`, and household-size/AGI questionnaire fields. An approved, non-expired record applies to that student's fees across **all** of their programs — see `get_active_sliding_scale()` / `get_sliding_scale_for_program()` / `get_student_balance_data()` in `programs/utils/balances.py`. Parents apply from the Payments page (`sliding_scale_apply`); Lead Mentors review from the `sliding_scale_review_list`/`sliding_scale_review_decide` views, which auto-delete uploaded `TaxForm` documents once a decision is made. The base/multiplier numbers used to suggest a discount percent live in the singleton `SlidingScaleSettings` model, editable from Portal Settings → Sliding Scale tab.
- **Application**: Multi-step resumable application records (in `applications/`). Applications store allergy/dietary/medical data as plain text in the `data` JSONField (`step5-student` key). If the `FILE_ENCRYPTION_KEY` is rotated and Student encrypted fields become garbled, run `python manage.py reencrypt_encrypted_data` (or the focused `python manage.py reencrypt_student_medical`) to re-write them. The generic command re-encrypts every encrypted model field — Student medical fields, `TaxForm.file` uploads, and any future `Encrypted*Field` — using the current `FILE_ENCRYPTION_KEY`, with old keys supplied via `--old-file-key`/`OLD_FILE_ENCRYPTION_KEY` or `--old-secret-key`/`OLD_SECRET_KEY`, and optional `--new-file-key`/`NEW_FILE_ENCRYPTION_KEY` to pre-encrypt to a key before it becomes the configured value (`--dry-run` previews changes). It tries the current key, then the supplied/legacy SECRET_KEY-derived keys, then converted Application source data (for Student medical fields only). See `programs/management/commands/reencrypt_encrypted_data.py`. **Legacy step keys**: applications started before the step-key rename hold their `data` under `step5`/`step6`/`step7`/`step8`/`step6_handoff` — never create code that reads/writes those names. Use `normalize_step_keys()` (module-level, `applications/models.py`) or `Application.normalize_step_data(save=True)` to merge any legacy keys into the current names (`step5-student`, `step6-experience`, `step7-primaryparent`, `step8-secondaryparent`, `step7_handoff`), keeping the more complete dict when both exist. The review detail/edit views, conversion (`convert_application_to_student`), `_save_step_data`, and `_student_initial_for` all normalize before reading/writing `application.data`; do the same in any new code that touches it.
- **AttendanceEvent / Session**: RFID-based check-in/out tracking. Visitor names are denormalized on these records; Lead Mentors can manage and merge inconsistent visitor names via the **Visitor Management** tool (`VisitorManagementView`) to ensure standardized reporting. The **Hours Chart** page (`/attendance/hours-chart/`, `attendance_hours_chart_view`) shows a bar chart of total hours per student for a selected program with configurable average-hours/week reference lines, date-range filtering, and PNG download. The **All Program Entries** page (`/attendance/all/`, `AllAttendanceView` — Lead Mentor-only) shows the master list of `AttendanceSession`s. It supports GET query-param filters: `program_id`, `person_type` (`student`/`mentor`/`visitor`), `status` (`open`/`closed`), and a date range via `range` (`today`/`yesterday`/`week`/`month`/`custom` with `start_date`/`end_date`), plus `export=csv`/`export=xlsx` to download the filtered/sorted list. Filter logic lives in `_filter_attendance_sessions`/`_attendance_date_bounds`, and sorting uses the `{% sort_url %}` tag which preserves all GET params.
- **DigitalSignoutConfig / DigitalSignout / StudentPresence**: Digital sign-out stations for parents/guardians. Like `KioskConfig`, a `DigitalSignoutConfig` links a label to a program and serves a **login-exempt** public page at `/signout/<config_id>/` (added to `EXEMPT_PATH_PREFIXES`); inactive configs return the project's `Http404` → redirect-to-home behavior. The page (template `kiosk/signout.html`) lists active enrolled students and lets a parent pick one and draw a signature on a canvas using the vendored **signature_pad** JS library (`attendance/static/vendor/signature_pad/5.0.4/`). Each submission creates a `DigitalSignout` (program + student + `signed_by_name` + `signature` PNG FileField + `signed_at`), decoded server-side from a `data:image/png;base64,...` payload and validated in `attendance/signout_views.py` (`_decode_signature`). Both models are managed in the Django admin under Attendance. The station uses a **redirect-after-submit (PRG)** flow: a successful POST redirects to a GET confirmation URL (`?done=<pk>`), and the "Done" button navigates back to a fresh form, so refreshing/re-loading never re-submits or duplicates a record. A student who already has a today's `DigitalSignout` is shown dimmed with a "Signed out" badge and can't be signed out again that day; tapping a dimmed name reveals a "…signed out. Click here to undo" confirm that deletes the today's sign-out via an `action=undo&signout_id=<pk>` POST (redirecting back with `?notice=undone`) — implemented as a `fetch` POST reading the CSRF + action from the hidden `#undoForm` (see `templates/kiosk/signout.html`), so it works on unreliable tablet browsers. The signature canvas is sized to its on-screen layout (`fitCanvas`) so strokes stay aligned 1:1 with the finger/stylus. After picking a student, the parent picks who is signing out from a dropdown (`#signedBySelect`) populated from `parents_by_student` (derived from the student's linked `Adult` accounts with `is_parent=True`, passed via `json_script`) with a manual fallback (`__manual__` → typed name); the submit listener writes the chosen name into the hidden `#signedByNameHidden` field that the server reads as `signed_by_name`. Parents/guardians are linked to students via `AdultStudentRelationship` (the same `Student.adults` related name). The station's **unlock is armed by a mentor** from the program page and stays open on the tablet for **8 hours** (`_COOKIE_MAX_AGE = 8*60*60` in `attendance/signout_utils.py` — separate from the 7-day kiosk unlock in `attendance/kiosk_utils.py`; don't touch that). **Per-day present/absent attendance** lives in the `StudentPresence` model (`attendance/models.py`): `program` + `student` + `date` (default `timezone.localdate()`) + `status` (`present`/`absent`) + `marked_by` FK (nullable User), with `unique_together=("program","student","date")` so toggling overwrites today's row (views use `update_or_create`). Mentors manage it from the program page's "Who's Here Today?" card (`ProgramDigitalSignoutView` POST `action=mark_present|mark_absent&student_id=...` → PRG redirect). **Unmarked students default to absent; only students explicitly marked present appear on the tablet picker** (absent/unmarked students get no sign-out button), and submitting a student who isn't marked present is rejected — see `attendance/signout_views.py` where only today's `PRESENT` ids are shown. A single program feature, `signout-sheet` (renamed to **"Parent sign-outs"**), gates both the printable sign-out sheet button and the "Digital Sign-out" button on the program detail page (`templates/programs/detail.html`), so one setting turns both on/off (fresh-DB default lives in migration `0041`; existing rows are renamed by data migration `0112`).
- **OutreachEvent / OutreachShift / OutreachSignup**: Community events that students can sign up for as "champions" (leads) or "helpers". An `OutreachEvent` has no date/time or capacity fields of its own; instead it has one or more `OutreachShift` rows (`date`, `start_time`, `end_time`, `max_champions`, `max_helpers`) via the `shifts` related name — e.g. an all-day event might have a morning shift and an afternoon shift, each with its own champion/helper capacity. `OutreachEvent.start_date`/`start_time`/`end_date`/`end_time`/`is_past`/`duration_hours` are **derived properties** computed from the first/last shift (ordered by `OutreachShift.Meta.ordering`), never stored directly — use `event.ordered_shifts`/`prefetch_related("shifts")` to avoid N+1 queries on list pages. `OutreachSignup` belongs to a specific `OutreachShift` (not the event directly — `unique_together = ("student", "shift")`), so a student can sign up for multiple shifts of the same event; `OutreachSignup.event` is a read-only convenience property (`self.shift.event`). The event create/edit form (`OutreachEventForm`) manages shifts via an inline `OutreachShiftFormSet` (`OutreachShiftFormSetMixin` in `outreach/views.py`), which requires at least one shift. Sign-up/cancel/manage-signups views and URLs are shift-scoped (`outreach:shift_signup`/`shift_cancel`/`shift_manage_signups`, keyed on `shift_pk`); `can_user_write(user, "outreach", obj)` in `programs/permission_views.py` grants Students write access to an `OutreachEvent` only if they champion one of its shifts, and to an `OutreachShift` only if they champion that specific shift. Outreach events are tied to a specific **Program** and can be enabled or disabled per program via the 'outreach' feature toggle in `ProgramFeature`. Access is program-scoped (e.g. `/programs/<id>/outreach/`). Mentors can also volunteer to support shifts via `OutreachMentorSignup` (`adult` FK + `shift` FK, `unique_together = ("adult", "shift")`, no role/capacity limit — any number of mentors may support a shift). Only mentors may sign up: the `outreach:shift_mentor_signup`/`shift_mentor_cancel` views require `user_is_mentor(user)` or the LeadMentor role, and link the user's `Adult` profile. Mentor names are shown on event cards to everyone; the list view passes `viewer_is_mentor` and `mentor_signup_shift_ids` template context. The mentor dashboard (`DashboardView` in `portal/views.py`) also surfaces upcoming support signups as `mentor_outreach_signups` (past shifts excluded). `OutreachSignup` also carries `checked_in_at` / `checked_out_at` timestamps and a computed `attended_hours` property (= check_out − check_in when both set, else `None`). A signup is **finalized** once both timestamps are recorded and the shift is past; `compute_outreach_stats` in `outreach/utils.py` credits **Completed** hours from finalized signups and **Pending** hours from upcoming signups plus past signups that are not yet finalized. Past-shift gating is per-shift, not per-event: once a shift's scheduled end time passes, students (including champions) can no longer sign up, cancel, or manage signups on that shift — only mentors and Lead Mentors retain write access. The check-in page (`OutreachShiftCheckInView`, URL `outreach:shift_check_in`) is a phone-first authenticated view where mentors and champions record attendance via `check_in`/`check_out`/`check_in_all`/`check_out_all` POST actions; champions lose access once all signups are stamped or 4 hours after shift end (whichever first). Walk-ups can be added on the spot via a `walk_up` action (creates a Helper signup bypassing capacity, stamps check-in immediately). Operators can also correct or backdate recorded times after the fact: each student row has an inline "edit times" form posting a `set_times` action (validated by `OutreachSetTimesForm` in `outreach/forms.py`, with datetime-local inputs; a check-out requires a check-in and can't precede it). It's gated by the same `can_operate_checkin` rule, so mentors/Lead Mentors always can edit and champions only until their access lapses — letting event staff fix a missed/wrong check-in without needing Django admin.
- **AddressGeocode**: Cache of geocoded student addresses used by the program map view (in `programs/views/programs.py` `ProgramStudentMapView`). Addresses are geocoded server-side via configurable backends (Mapbox and Nominatim/OpenStreetMap by default) and cached keyed by a normalized address (see `programs/utils/geocoding.py`); students who share an address reuse the same row. The map page renders markers from pre-geocoded coordinates (no client-side geocoding) and `fitBounds` to the students' area. Lead mentors can pre-populate the cache with `python manage.py geocode_student_addresses` (use `--retry-missing` to re-attempt addresses that previously failed). For Parents/Students the map is a "Carpool Map" (buttons on their dashboards) and only includes students with `directory_consent=True`. Tuning knobs live in settings: `GEOCODING_BACKENDS`, `MAPBOX_ACCESS_TOKEN`, `GEOCODING_URL`, `GEOCODING_USER_AGENT`, `GEOCODING_TIMEOUT`, `GEOCODING_DELAY_SECONDS`.
- **BackgroundCheck**: A single PA clearance (PA State Police, PA Child Abuse/Act 151, or FBI) held by a **Student** or an **Adult** (exactly one of `student`/`adult` is set; not enforced in the DB because a student becoming an alumni may hold both records). Per PA rules clearances are valid 5 years, so each row stores `cleared` and the `obtained_date` (when it became active); `expiration_date` is a **derived property** = `obtained_date + 5 years` (never stored). The university holds the actual forms — we only track status/dates, no uploads. **Whether a student *requires* clearances is always derived**, never cached: `Student.requires_background_check()` (17 or older on Sept 1 of the current academic year) and `Student.needs_background_check()` (required **and** missing a valid clearance of one of the three types) in `programs/models.py`. List pages flag "BG Check Needed" via the `needs_bg` template tag (in `programs/templatetags/form_tags.py`). `Enrollment.post_save` auto-sets `Enrollment.clearance_due` for enrolled students who need checks (see `programs/signals.py`). Exposed read-only on all Adult/Student view screens and editable inline via the `BackgroundChecksForm` (in `programs/forms.py`), wired into the student/adult/mentor/parent update views through the `BackgroundChecksInlineMixin` (in `programs/views/mixins.py`). Editing is gated on `can_user_write('background_checks', obj)` (Lead Mentors only by default); other roles see clearances read-only. Also managed in admin via `BackgroundCheckInline`.
- **OrderItem / Order** (in `orders/`): Two-level purchase/order requests, replacing the team's Google Form workflow and the legacy single-row `PurchaseOrder` model (removed in migration `0003`). Students and mentors place **`OrderItem`** requests with `item_name`, `quantity` (Decimal, default 1, min 0.01), `unit_price` (optional/min 0; `OrderItem.total` is `None` when missing), `url`, `notes`, an optional `tag` (nullable FK `SET_NULL` to `ItemTag`, related name `order_items`), `requested_by`/`requested_at`, `program` (FK `SET_NULL`, related name `order_items`), and an optional `vendor` (FK `SET_NULL` to `Vendor`, related name `order_items`, plus `vendor_name`/`vendor_url` snapshots mirroring the order's — set via the request form's own vendor picker with the same `NOT_LISTED_VENDOR` sentinel; display via `OrderItem.vendor_name_display`, which falls back to the FK's name for items created directly). An item with no `order` sits in the unassigned **request pool** (the Requests section of the `order_list` page); its **status is always derived, never stored** via `OrderItem.status_key` (`"pending"` = unassigned pool, `"ready"` = in an order ready to be placed, `"ordered"`/`"shipped"`/`"received"` = from the parent order) and a custom `get_status_display()` label method (Pool→"Pending", pending-order item→"Ready to order"). Mentors/Lead Mentors group pool items into **`Order`** rows, which represent items placed together with one vendor: `program` (FK `SET_NULL`, null/blank, related name `orders`), `vendor` (nullable FK to `Vendor`, related name `orders`), `vendor_name`/`vendor_url` **snapshot fields**, `notes`, `status` (`pending`/`ordered`/`shipped`/`received`), `created_by`/`created_at`, `ordered_at`/`ordered_by`, `shipping_carrier` (nullable FK to `ShippingCarrier`, related name `orders`)/`tracking_number`/`shipped_date`/`delivery_estimate`, `shipping_cost`/`tax` (nullable DecimalFields, both included in the total), plus `item_count` and `total` properties. `Order.total` sums the priced items plus posted shipping/tax (coercing strings so it is safe on fresh instances) and returns `None` while everything is unpriced with no extras; `Order.tracking_url` derives a clickable link from the carrier's `tracking_url_template` when both a `tracking_number` and a carrier are set. Grouped items are `OrderItem(order=...)` (CASCADE FK, related name `items`). **Vendor** (`orders/models.py`) is an org-wide, Lead-Mentor-managed reference list of suppliers: `name` (unique), `website`, `contact_email`, `contact_phone`, `notes`; CRUD lives in `VendorListView`/`VendorCreateView`/`VendorUpdateView`/`VendorDeleteView` (all `OrderProgramMixin` + `LeadMentorRequiredMixin`, URLs `orders:vendor_list`/`vendor_create`/`vendor_edit`/`vendor_delete`, templates `templates/orders/vendor_*.html`, "Vendors" button next to export buttons on the orders list/archive). **ShippingCarrier** (`orders/models.py`) is a parallel org-wide, Lead-Mentor-managed reference list of shipping companies: `name` (unique) plus a `tracking_url_template` containing a `{number}` placeholder (required by `ShippingCarrierForm.clean_tracking_url_template`); `format_tracking_url(number)` fills the template in. CRUD lives in `ShippingCarrierList/Create/Update/DeleteView` (URLs `orders:carrier_list`/`carrier_create`/`carrier_edit`/`carrier_delete`, templates `templates/orders/carrier_*.html`, "Shipping Companies" button next to "Vendors" on the orders list/archive). Deleting a carrier NULLs the order's FK (SET_NULL) but keeps the tracking number (shown as plain text, no link). **ItemTag** (`orders/models.py`) is an org-wide label list (the team's old "badges" idea): `name` (unique) plus a `color` hex string (default `#0000ff`), displayed as a colored `tag-badge` pill. CRUD lives in `ItemTagList/Create/Update/DeleteView` (URLs `orders:tag_list`/`tag_create`/`tag_edit`/`tag_delete`, templates `templates/orders/tag_*.html`, "Item Labels" button); `OrderItemForm` exposes `tag` as an optional `ModelChoiceField` (empty label "No tag", queryset set in `__init__` to `ItemTag.objects.order_by("name")`). Deleting a tag NULLs `OrderItem.tag` but keeps the item. `seed_db` seeds three carriers (UPS/FedEx/USPS via `_seed_shipping_carriers`) and five tags (Drivetrain/Marketing/Electrical/Programming/General via `_seed_item_tags`), and `_seed_orders` assigns a demo carrier, tracking number, shipping cost, and tax so the sample order total shows the authentic amount. The order grouping form (`OrderForm` in `orders/forms.py`) lets the mentor pick a program, choose a vendor from a **required** `vendor_choice` dropdown (blank is rejected; the sentinel `NOT_LISTED_VENDOR = "__not_listed__"` shows "Not listed - I'll specify below" and the custom `vendor_name` is optional even then), and select the requested items to include via an `items` checkbox list of unassigned `OrderItem`s (create only - item membership is managed from the detail page afterwards). The form also carries nullable `shipping_cost`/`tax` fields so an order's freight and sales-tax can be posted up front - both are included in `Order.total` (and shown in the detail page total breakdown). Editing an order that used a deleted/custom vendor pre-selects the sentinel. Build/refresh the vendor dropdown from `Vendor.objects.all()` in `OrderForm.__init__` (no cache) and pass `not_listed_vendor` to templates. The vendor dropdown is display/reference only - students can't create orders at all (gated by `OrderStaffRequiredMixin`, mentor/Lead Mentor only) and only Lead Mentors manage the vendor list. Access is gated per section in `programs/permission_views.py` using **four granular order sections** defined in `ORDERS_SECTIONS`: `orders-view` ("Orders - See requested orders"), `orders-request` ("Orders - Place item request"), `orders-manage` ("Orders - Place new orders"), and `orders-shipping` ("Orders - Add shipping"). All are in `RolePermission.SECTION_CHOICES` (Lead Mentors flip them on/off per role from Portal Settings -> Permissions) and split from the legacy single `orders` section by data migration `0114`. `can_user_read` returns True for Student/Mentor; the `orders-view` row governs page/read access (default on), the action sections are write-gated and always readable. Parents/alumni are always denied all four. `can_user_write` treats each section as its own master switch (default on) with per-object ownership rules: `orders-request` allows creating requests (obj None) and editing one's own unassigned `OrderItem`s (`requested_by_id == user.pk and order_id is None`); `orders-manage` allows mentors to create/edit their own pending `Order`s and add/remove items on them (students never manage orders); `orders-shipping` lets any mentor with the toggle record tracking on placed orders' shipping; students are only ever granted `orders-request`. `can_user_delete` is Lead Mentor-only for all four. The list page ("Active Orders") is grouped **by vendor** (`_group_by_vendor` in `orders/views.py`, blank vendor -> "No vendor specified"); `OrderDetailView` is read-accessible (students can follow status/shipping), with item management gated on `orders-manage`, the shipping form gated on `orders-shipping` (shipping details render read-only otherwise), and the "Request an Item" / "Place Order" buttons gated on `orders-request` / `orders-manage`. `OrderDeleteView` returns grouped items to the pool before deleting (CASCADE would destroy them). Leadership views: `OrderAddItemsView`/`OrderRemoveItemView` add or return items to the pool, `OrderMarkOrderedView` (pending→ordered; also un-marks a shipped order back to ordered)/`OrderMarkShippedView` (ordered→shipped)/`OrderMarkReceivedView` (shipped→received)/`OrderMarkPendingView` (ordered/shipped/received→pending). **Only `received` orders appear in the `order_archive`** (kept for budget/finance); placed/shipped orders stay on the active list so mentors can still record shipping details, and `OrderShippingUpdateView` (URL `order_update_shipping`, `ShippingInfoForm`) edits the shipping/tracking fields from the detail page - `ShippingInfoForm`'s carrier field is a `ModelChoiceField` populated from `ShippingCarrier.objects.order_by("name")` in `__init__` with an empty "No carrier" choice. Exports moved to **line-item level** for budgeting (CSV/XLSX from the list = pool + non-received order items; from the archive = received order items), with columns including Program, Item, Quantity, Unit Price, Total, Link, Order (#pk), Vendor, Vendor Website, Requested By, Requested On, Notes, Tag, Status (the **item**'s derived status), Ordered On; exports are Lead Mentor-only via `_OrderExportMixin`. Student access is **per-program** via the `ProgramFeature` key `"orders"` (`OrderProgramMixin` raises Http404 when the program lacks the feature; mentors/Lead Mentors are always allowed, and the orders pages are org-wide anyway). Nav wiring is unchanged: `GoSAdminPortal/context_processors.py` exposes `student_orders_programs`/`current_program_has_orders`; students get an "Order Requests" nav entry per qualifying program (gated on the program's `orders` feature — `seed_db` registers that feature and enables it on the current flagship program so seeded students see the link), mentors get a dropdown entry, and the program detail page shows an "Order Requests" button (gated on `can_write` for staff; students reach it via the nav). URL names preserved: `order_list`/`order_archive`; added `order_detail`, `order_add_items`, `order_remove_item`, `item_create`, `item_edit`, `item_delete` plus the `carrier_*`/`tag_*` reference-list URLs. `seed_db` seeds 8 common robotics vendors (`_seed_vendors`) plus a handful of request items and one grouped order (`_seed_orders`, guarded so re-seeding never duplicates). Registered in Django admin (`orders/admin.py`, with an `OrderItemInline` on `Order`). Tests in `orders/tests/test_orders.py`, `orders/tests/test_vendors.py`, and `orders/tests/test_shipping_carriers.py`, plus a migration `0003` that drops `PurchaseOrder`.
- **MentorAgreement / MentorAgreementAcceptance**: Versioned documents that mentors must accept before accessing the portal. Each `MentorAgreement` is identified by a `slug` (grouping versions of the same document) with a `version` number; `MentorAgreementAcceptance` records which adults have accepted which version. Content can be provided as markdown (`content` field) or an uploaded document (`document` field — PDF, etc.), or both. Lead Mentors manage agreements from Portal Settings → Agreements tab: create, update versions, activate/deactivate, and delete. Editing content or uploading a new document automatically creates a new version; metadata-only edits (title, is_active) update in place. The middleware (`MentorAgreementMiddleware`) redirects mentors who have **not accepted all active agreements** to `/mentor-agreement/`, which shows all pending agreements and an "I Agree to All" button. `Adult.has_accepted_current_agreement()` checks acceptance across all active agreements. Activating a new version auto-deactivates old versions of the same slug, requiring re-acceptance. Seeded with `python manage.py seed_mentor_agreement`. Controlled by `MENTOR_AGREEMENT_ENABLED` (defaults to `not TESTING`).

## Security and Permissions

- **Key rotation**: Encrypted fields always use the current `FILE_ENCRYPTION_KEY`. `SECRET_KEY_FALLBACKS` is only populated when `OLD_SECRET_KEY` is set (empty otherwise, so Django's `security.W021` check stays silent on deploy builds). If `SECRET_KEY` or `FILE_ENCRYPTION_KEY` is rotated, re-encrypt existing encrypted data with `python manage.py reencrypt_encrypted_data` (old keys via `--old-file-key`/`OLD_FILE_ENCRYPTION_KEY` or `--old-secret-key`/`OLD_SECRET_KEY`, optional pre-encryption target via `--new-file-key`/`NEW_FILE_ENCRYPTION_KEY`, preview via `--dry-run`).
- **Global Auth**: `LoginRequiredMiddleware` in `GoSAdminPortal/middleware.py` enforces login globally. Unknown paths redirect to login (not bypass it).
- **Exempt URLs**: `/apply/`, `/accounts/*`, `admin/`, `privacy_policy`, `non_discrimination_policy`, and static/media. These are listed in `EXEMPT_URL_NAMES` inside the middleware.
- **Wizard Rate Limiting**: The public wizard (`/apply/`) is throttled because it's anonymous and login-exempt. `ApplyRateLimitMiddleware` caps each client IP at `APPLY_IP_POST_LIMIT` (default 10) POSTs per `APPLY_IP_POST_WINDOW_SECONDS` (default 60). OTP limits are enforced in the views via `applications/rate_limiting.py`: `APPLY_OTP_SEND_LIMIT` (default 5) code requests per email per hour and `APPLY_OTP_VERIFY_LIMIT` (default 10) verify attempts per application per hour. All limits are disabled while running tests (`APPLY_RATE_LIMIT_ENABLED` defaults to `not TESTING`) because the shared test-client IP and process-local cache would otherwise leak hits between tests; re-enable in tests with `override_settings(APPLY_RATE_LIMIT_ENABLED=True, TESTING=False)` (clear the cache in `setUp`). Counters use the Django cache — configure a shared backend (`CACHES` via `CACHE_BACKEND`/`CACHE_LOCATION`) in production so limits apply across app servers. Exceeded limits return HTTP 429 with a `Retry-After` header and render `templates/429.html`.
- **Roles**: Determined by `get_user_role(user)` in `programs/permission_views.py`. Priority order: `LeadMentor` (superuser or `LeadMentor` group) → `Mentor` → `Parent` → `Alumni` → `Student` → `Staff`/None. Because an Adult can hold several roles at once (e.g. a parent who also mentors), `get_user_role` alone is not enough to answer "is this person a parent?" — use the flag helpers `user_is_parent(user)`, `user_is_mentor(user)`, `user_is_alumni(user)`, and `user_is_mentor_or_lead(user)` (same file) for role-specific features like the Payments page and balance sheets. Finance sections in `can_user_read` treat any parent as a parent even if they'd otherwise resolve to `Mentor`/`Alumni`.
- **Dynamic Permissions**: `RolePermission` model lets Lead Mentors configure per-section read/write access for each role. Check with `can_user_read(user, section, obj=None)` and `can_user_write(user, section, obj=None)`. By default Mentors get read+write on the `attendance` section (so they can close stale sessions on the Who's Here Now page and manage RFID cards); deletion is still blocked for them via `can_user_delete()`.
- **View Mixins**: Use `LeadMentorRequiredMixin`, `DynamicReadPermissionMixin`, or `DynamicWritePermissionMixin` (all in `programs/permission_views.py`). Do NOT use raw `has_perm()` checks for portal views.
- **Object-Level Access**: `can_user_read`/`can_user_write` accept an `obj` argument for per-object checks (e.g., a Parent can only read their own students). Always pass `obj` when checking access to a specific record.
- **Mentor Adult Access**: Mentors can only view Adults with `is_parent=True` who have a student in an active program. This is enforced in both the queryset and `can_user_read`.
- **Mentor Program Visibility**: Mentors see current and upcoming programs (never past/inactive ones). Enforced in `ProgramListView.get_queryset` (`active=True`, not ended) and in `can_user_read(user, "programs", obj)` via `obj.status in ("Active", "Upcoming")`; the mentor dashboard's program cards use the same rule. Mentors can also send program emails (`ProgramEmailView`) for programs they can read — the view requires the Mentor/LeadMentor role plus `can_user_read` on the program, so parents/students are always denied; program-wide messaging without a fixed program stays Lead Mentor-only. The home program list shows mentors all `active=True` programs: past ones render as plain text (the template gates each link with `{% can_read user 'programs' program %}`), and inactive programs stay hidden from their queryset.
- **One Lead Mentor group**: There is only `"LeadMentor"` (no space). A single membership grants access to all Lead Mentor features including application review.
- **Role permissions**: Always pass obj to can_user_read/can_user_write.
- **Reuse existing helper/utility functions**: Use functions like `active_students_in_program()` and `user_is_mentor_or_lead()`, not inline filters.

## Testing Strategy and Contribution

- **Upgrade-Aware Test Runner**: `TEST_RUNNER = "GoSAdminPortal.test_runner.UpgradeAwareTestRunner"` (see `GoSAdminPortal/test_runner.py`) escalates Django's `RemovedInDjango70Warning`/`RemovedInNextVersionWarning` to test errors, so any use of APIs deprecated in the current Django release fails the suite. Do not disable this; fix the deprecated usage instead.
- **Location**: Tests live in `programs/tests/`, `applications/tests/`, and `attendance/tests/` (with `test_models.py`, `test_views.py`, `test_kiosk.py`, `test_permissions.py`, `test_reliability.py`, `test_who_is_here.py`).
- **Story Integration Tests**: For complex lifecycles (e.g., Application -> Conversion -> Financials), use "Story" tests that exercise multiple views and signals in a single test case (see `programs/tests/test_integration_flows.py` for examples). These help catch regressions in side-effects (like emails or balance calculations) that unit tests often miss.
- **TDD Requirement**: When fixing bugs, add a reproducer test file (e.g., `test_issue_reproduction.py`) before applying the fix.
- **UI Automation**: For JS-heavy components (like DualListbox or the multi-step application wizard), consider browser-based tests using Playwright.
- **Scope**: Include model validation, forms, services, and view logic.
- **Bandit**: If adding new tests that have hard-coded passwords, add `# nosec B106` on the line with the password string.
- **Groups in tests**: Use `Group.objects.get_or_create(name="LeadMentor")` (no space). Do not create a `"Lead Mentors"` group — it no longer exists.
- Add unit tests for new business logic.
- Keep changes minimal and avoid large refactors in feature tasks.
- Do not rename files without a valid technical reason.
- Make small, targeted changes instead of building for hypothetical future needs.
- Try to run parallelized tests (`python manage.py test` commands with the `--parallel=16` option) to speed up work. If traces are needed, run without parallelization.

## Reliability Requirements

### Pre-merge Checks (CI must pass)
- All tests pass (`python manage.py test --parallel`)
- Type check: `mypy --strict` (configured via `pyproject.toml`)
- Security scan: `bandit -r .`
- Migration check: `python manage.py makemigrations --check --dry-run`
- No `console.log`/`debug`/`print` statements in production code

### Database Safety
- **Never** generate raw SQL or run raw SQL in production without a rollback plan
- All data migrations must have `reverse_code` or explicit `--no-reverse` justification
- Run `python manage.py find_disconnected_accounts` before/after user-facing changes
- Seed commands (`seed_db`, `seed_mentor_agreement`) must be idempotent
- Document how to rollback a bad migration or what steps to take if something goes wrong

### Test Coverage Targets
- New views: ≥1 integration test covering permission matrix
- New models: ≥1 test for each custom save/clean/property
- Signal receivers: test both create and update paths
- Management commands: test `--dry-run` and actual execution
- Migration tests: use `django-test-migrations` for critical schema changes

## Agent-Specific Tips (Junie, Copilot, OpenCode, etc.)

- Prefer role-specific template folders (`adults/`, `parents/`, `mentors/`, `alumni/`).
- The `applications` app supersedes legacy models in `programs`.
- Use `run_ci.ps1` (or equivalent) before finishing a task.
- Search the codebase to infer structure; `programs/permission_views.py`, `signals.py`, and `utils.py` have important reusable code blocks. Reuse those whenever possible, or add similar code blocks into these files.
- When adding a new view, pick the right mixin from `programs/permission_views.py`: `LeadMentorRequiredMixin` for Lead Mentor-only actions, `DynamicReadPermissionMixin` / `DynamicWritePermissionMixin` (with `permission_section`) for role-configurable pages, `LoginRequiredMixin` for any authenticated user.
- When filtering querysets by role, use `StudentQuerysetRoleMixin.filter_students_by_role()` (in `programs/views.py`) instead of duplicating the Parent/Student filter pattern.
- When limiting a student queryset to active students, use `active_students()` (non-graduated) for global lists and `active_students_in_program(program)` (active enrollment + non-graduated) for program-scoped lists, both in `programs/utils.py`. Don't build the `enrollment__active=True, graduated=False` filter inline.
- `signals.py` uses string-based lazy senders (`sender="programs.Adult"`) — not lambdas. Follow this pattern for any new signal receivers.
- The `PortalSettingsView` handles GET only. Permission updates, team, crew, subteam, and agreement changes each have their own dedicated view (`PortalPermissionsUpdateView`, `PortalTeamView`, `PortalCrewView`, `PortalSubteamView`, `PortalAgreementView`).
