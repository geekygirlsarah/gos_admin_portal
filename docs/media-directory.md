# Media Directory Guide

This guide describes the upload paths defined by the application and how to
review old directories safely. It is not a live inventory of production: the
contents of the configured `MEDIA_ROOT` vary by deployment and may include
older uploads, retained transition copies, interrupted copies, or files written
outside the application.

## What `MEDIA_ROOT` contains

`MEDIA_ROOT` is the root for user- and administrator-uploaded files. The current
settings set it to the relative path `media/`, which is resolved from the
process working directory, not inherently from `BASE_DIR`. On the production
instance previously checked, the working directory was
`/opt/render/project/src` and the operator confirmed a persistent mount at
`/opt/render/project/src/media`. Verify the working directory, resolved storage
location, and disk mount for each new instance before inspecting or backing up
files. `MEDIA_URL` (`/media/`) is a URL prefix, not a separate directory.
`STATIC_ROOT` (`staticfiles/`) is for collected site assets and is separate from
uploaded media; do not clean it as part of media retention.

The following paths are generated by current models or upload code. The
`<...>` parts are variable path components, not literal directory names.

| Path below `MEDIA_ROOT` | Purpose and handling |
| --- | --- |
| `private/student_photos/<organization_id>/` | Current student profile photos and photo paths copied into student history events. Filenames are generated by the application. Access is intended through the authorized student-photo endpoint. The 90-day `cleanup_student_photos` workflow is limited to eligible, unreferenced files under this prefix. |
| `private/application_documents/<organization_id>/<application_id>/` | Current signed/completed application-document uploads. Treat as sensitive; access is through authorized application endpoints. |
| `photos/adults/` | Current adult profile photos and the paths recorded in adult history events. The path is not a privacy boundary; see the direct-media note below. |
| `student_documents/<student_id>/` | Signed program-enrollment documents attached to a student. The file field uses application-level encryption; these are not part of the private-media transition or student-photo cleanup commands. |
| `program_documents/<program_id>/` | Blank program documents made available to applicants to download and complete. |
| `mentor_agreements/` | Uploaded source documents attached to mentor-agreement definitions. |
| `agreement_submissions/<adult_id>/` | Signed copies submitted for mentor agreements. Treat as sensitive. |
| `tax_forms/` | Tax documents uploaded for sliding-scale verification. The file field uses application-level encryption; treat as sensitive and retain only under the applicable records policy. |
| `digital_signouts/<configuration_id>/` | Digital sign-out signatures. The file field uses application-level encryption; treat as sensitive. |
| `guest_forms/<form_slug>/` | Source forms (for example, blank PDFs) presented to guests. |
| `guest_form_submissions/<form_slug>/` | Files submitted with guest forms; these may contain personal information. |
| `travel/permission_forms/<program_id>/` | Permission-form files attached to travel events. These may contain sensitive information. |
| `badge_icons/<badge_id-or-new>/` | Badge icon images. A `new` component can be used when an icon is saved before its badge has an ID. |
| `org_logos/` | Organization logo uploads; filenames include the organization slug and a generated suffix. |

Paths are based on current upload definitions in `programs/models/`,
`applications/models.py`, `attendance/models.py`, `guest_forms/models.py`,
`travel/models.py`, `badges/models.py`, and `programs/views/portal_settings.py`.
Uploads may also leave older layouts after a model's path changes.

## Known legacy photo and document paths

These are older paths that can remain on disk after the application has moved
the database reference to a newer location:

| Legacy path | What it may contain | What the application does |
| --- | --- | --- |
| `photos/students/` | Student photos uploaded before the private student-photo path was introduced. | The `transition_private_media` command can copy supported referenced photos to `private/student_photos/` and update their current field reference. It deliberately keeps the source file. |
| `photos/mentors/` | Mentor profile photos from the earlier mentor model/path. | The current adult profile upload path is `photos/adults/`; there is no general cleanup workflow for this legacy directory. |
| `application_documents/` | Signed application documents uploaded before the organization-scoped private path was introduced. | The transition command can copy supported referenced files to `private/application_documents/` and update their current field reference. It deliberately keeps the source file. |
| `signed/` | A possible earlier signed mentor-agreement submission path; test fixtures contain references, but production media use is unknown. | Direct Django media requests are denied. Existing records can be downloaded only through the tenant-scoped agreement submission endpoint. |

The transition command is read-only unless explicitly run with `--execute` and
does not purge legacy originals. A file under an old path is not necessarily
orphaned: current model fields, another record, a retained history event, a
backup, or an interrupted transition may still matter. History records store
file paths, not copies of image contents, so keeping a path in history does not
preserve the image itself.

Replacing a student photo can also leave an older file under
`private/student_photos/`. The `cleanup_student_photos` command is specific to
that private prefix: its default is a read-only preview, and an operator must
inventory the file and allow the full 90-day recovery window before eligible
files can be removed. It does not clean `photos/students/`, `photos/mentors/`,
adult photos, signed documents, or other directories. See
[`operations.md`](./operations.md#retaining-replaced-private-student-photos)
for its exact workflow and safeguards.

## Access and sensitivity

The Django direct-media handler denies paths beginning with
`agreement_submissions/`, `application_documents/`, `photos/students/`,
`private/`, and `signed/`. That protects those paths only when requests go
through Django. A proxy, CDN, or separate storage origin may serve files
independently and must be checked as well.
Other directory names are not access controls: for example, current
`photos/adults/` and legacy `photos/mentors/` paths are not in Django's
direct-media deny list. Treat uploads as sensitive according to their contents,
and verify direct and authorized access through the actual production serving
path before changing storage or access rules. See
[`security.md`](./security.md#protected-media-and-zero-database-request-invariant).

## Read-only directory review

First confirm the production mount and available space. These example commands
list directory names and aggregate sizes without printing file contents; paths
and names can still reveal organizational information, so keep output private.

```bash
MEDIA_ROOT=/opt/render/project/src/media
df -h "$MEDIA_ROOT"
find "$MEDIA_ROOT" -mindepth 1 -maxdepth 3 -type d -print
du -h -d 2 "$MEDIA_ROOT" | sort -h
```

If the live `MEDIA_ROOT` differs, use the confirmed path instead. Do not run
deletion commands while reviewing. Before classifying any folder or file as
removable:

1. Make and verify a coordinated database backup and a complete media backup;
   record their times and recovery locations securely.
2. Match the directory to the current model fields and any legacy migrations or
   transition tooling. Check current file-field references and relevant history
   before treating an unreferenced path as disposable.
3. Keep the 90-day private-photo policy separate from other uploads. Do not
   apply it to legacy photos, documents, signatures, or other directories.
4. For legacy student photos or signed application documents, review the
   read-only output from `python manage.py transition_private_media`. This
   command is an inventory/transition tool, not a deletion tool; manual-review
   cases need investigation and source files remain in place.
5. If a folder is still unexplained, stop and retain it until its owner,
   references, retention requirements, and recovery path are established. Any
   destructive cleanup requires a separately reviewed and approved procedure.

Do not share raw filenames or directory listings publicly: names or file
metadata may identify students, families, staff, or organizations.
